Case Study — AI Infrastructure

Platone

A hybrid edge / cloud voice assistant, grounded on a technical knowledge base.

Beyond answering from the knowledge base, it can search the web or give an unguarded opinion on request — only after a spoken "yes" — and switch register (technical, plain‑language, or consultative) per knowledge base.

Component placement, model choice per role, and fallback behavior are decided from measured results — not defaults or vendor reputation.

01

An evolved RAG — not just retrieve, then generate

1 · Retrieve — three steps a naive RAG does not have
Question + history → Rewrite → Hybrid search → Cross-encoder rerank → Score gate, τ = 0.1
REWRITE
Turns a follow-up into a question that stands on its own. In speech, people drop the subject: "and how long does that take?" carries no searchable term at all. Sent to a vector database as-is, it retrieves noise. The rewrite reads the conversation so far and restores what was left implicit — the entity, the constraint, the language — producing a query that can be searched without the conversation attached.
HYBRID SEARCH
Two retrieval methods, because each fails where the other works. Semantic search matches meaning, so it finds the right passage even when the wording is different — but it blurs exact tokens, and a part number or an acronym is only itself. Keyword search matches those literally and is useless on paraphrase. Both run on every query and their results are merged, so a question can be answered whether it was asked in the corpus's words or the user's.
RERANK
Re-reads the shortlist with the question in hand. Retrieval compares the question to passages that were indexed long before it was asked, so it is fast but approximate. The reranker takes only the surviving candidates and scores each one against the actual question, catching passages that merely look topical. What reaches the gate is a re-ordered shortlist, not raw search output.
SCORE GATE
One number decides which of two very different paths the turn takes. Everything after this point — whether the model is asked to answer, to judge, or to try again — depends on whether the best candidate clears the threshold.
2 · Above the threshold — the model states its own coverage
The expert model declares coverage as the first line of its answer. The marker is never spoken aloud; the labels below are the literal Italian strings the code matches on, kept here as they appear in the source.
COPERTO
Grounded answer, streamed from the documents.
PARZIALE
Grounded answer on what is covered, with an offer appended for the rest.
NON_COPERTO
No KB answer — the question is on topic but genuinely absent from the context. Goes to the offer stage instead of returning a partial answer.
marker missing
Answers anyway — fail-open, grounded-first. An ambiguous marker never causes silence. This holds in every trust policy, including strict: the retrieved context did clear the threshold, so the fallback is a grounded answer, not an abstention.
3 · Below the threshold — domain judge, then a second attempt
off-domain
Abstain. No second attempt: a low score plus an unrelated question is not worth another round-trip.
in-domain
Second pass. A constrained rewrite, then the same retrieval re-read with the numeric gate switched off (τ = −1), and the expert judges semantically whether the context answers the question — covered gives a grounded answer, NON_COPERTO goes to the offer stage.

The score is dropped on the second pass on purpose: a cross-encoder measures similarity between query and text, not whether the text answers the question. An honest rewrite could improve grounding while lowering the score; keyword stuffing did the opposite.

4 · Offer and consent — which capability is available is set per KB, in the trust policy
grounded → web only hybrid → web or opinion advisor → opinion only strict → no offer, abstain
Web search and opinion are the same two capabilities described under Features — available on request at any time. Here they surface as a fallback specifically because the KB fell short; the trust policy decides which ones are on the table.
The offer is spoken and lives exactly one turn. On the next turn an explicit choice runs that branch, a "no" closes it, and anything else is discarded and treated as a new question. A generic "yes" against a double offer is ambiguous, so Platone asks which one rather than picking for the user.
web
The rewriter builds a search query, the search engine returns already-extracted page content, and the answer opens by declaring it came from the internet. The engine is a one-line setting with no automatic runtime fallback: if the configured one fails, the turn says so and stops rather than silently degrading to a different engine.
opinion
A separate advisor model answers, using the retrieved context as background to reason from rather than as a constraint, and opens by declaring it is not from the documents.
branch empty
Abstain. A chosen branch that produces nothing does not fall back to guessing.

Platone keeps the familiar retrieve-then-generate shape, but rebuilds the decisions inside it. A naive RAG embeds a question, retrieves the top-k chunks, and pastes them into a prompt — even when those chunks do not actually answer it.

Here, follow-ups are first rewritten into standalone queries; retrieval is hybrid and reranked; and coverage is explicitly judged before the system is allowed to answer. When the documents fall short, Platone does not silently improvise: it retries retrieval, then asks for consent before offering a web search or a clearly-labelled opinion.

Not agentic RAG. The cascade above is application logic — an if/else path decided in code — not the model planning and calling its own tools. That was the preferred design regardless of model capability: every branch is deterministic, loggable, and reproducible after the fact, which an improvised tool-calling path is not.
02

Architecture — hybrid by design

That cascade decides what Platone answers. Where each step of it actually runs is a separate decision, and the one that shapes the rest of the system.

Latency-critical and privacy-sensitive stages run on the edge GPU; reasoning-heavy generation runs on cloud EU inference. Raw audio never leaves the edge node: in a typical follow-up turn only text crosses the boundary, over two round trips — once to rewrite the question, once to generate the answer.

Query rewriting and answer generation run on cloud EU inference, where a larger model is worth the round-trip. Qdrant runs in k3s/containerd; the application itself runs as a plain systemd service.
03

Features — what it can say, and how

Every knowledge base carries two independent settings: a trust policy — how far Platone is allowed to go for an answer — and a persona — how it says it. Neither is hard‑coded into the application; both live with the corpus and are read per turn, no restart required.

Persona — how it's said

tecnicodivulgativoconsulenziale

Asked why a component sits where it does, tecnico names the constraint and cites the section; divulgativo explains what would break otherwise and spells out the acronyms; consulenziale frames it as a trade‑off and separates what the document states from what it implies. Grounding rules, citations and the coverage gate stay fixed across all three — persona changes phrasing, not sourcing. The default is a literally empty prompt fragment, so the validated baseline behaviour is unchanged byte for byte.

Trust policy — how far it's allowed to go

groundedhybridadvisorstrict

Grounded (default) offers a web search when the knowledge base falls short. Hybrid lets the user choose between a web search or an opinion. Advisor only ever offers an opinion. Strict never offers anything beyond the documents — on a corpus of certified procedures, even the offer itself would be a risk, so it abstains cleanly instead. The coverage check is the same across policies; only the available options change.

Pronunciation control — an editor for how acronyms are said

A voice assistant on a technical corpus has to say things like ST36, MTC, or a company's own product codes out loud, and a speech model left alone will mangle them. A deterministic layer — no LLM in the path — rewrites them into a pronounceable form before synthesis, from a per-corpus map, a global map, and an automatic rule that ships off because it measured worse than doing nothing.

The part worth stealing is the editor built around it. The right rendering of an acronym cannot be derived from a rule — it is a judgment about how a word sounds — so the admin page lets you type a rendering and hear it immediately, one row at a time, and change it until it is right. Populating that map is seeded automatically: the acronyms were already extracted at ingest to help the speech-to-text model recognise them, and the same vocabulary is exactly what the speech synthesiser needs to pronounce them. One extraction, two opposite ends of the pipeline. Like the trust policy and the persona, the map travels with the knowledge base and is read per sentence, with no restart.

Beyond the knowledge base — web search and advisor

Both are capabilities the user has to ask for, one turn at a time. A web search reads content extracted from the result pages, and the spoken answer opens by saying it came from the internet. An advisor turn steps outside the documents entirely and gives a reasoned opinion, using retrieved context as background rather than constraint, and opens by saying it is not from the documents. Which of the two is even on the table is set by the corpus trust policy; neither ever runs silently, and neither is ever blended into a documented answer.

Decision path is visible per turn. A dedicated page shows the path a turn took — retrieval score, coverage verdict, domain judge, second pass, offer, user's choice — including branches not taken, with the reason why.

05

Key architectural decisions

Model routing by workload

ProblemIngestion, expert answers and query rewriting have opposite needs — one is batch and cheap, one needs a low time‑to‑first‑token, one needs to stay anchored to entities.
ChoiceConfigurable per‑role routing instead of one model for everything. Non‑reasoning models for ingest and expert; a larger model reserved for rewrite; reasoning models excluded from low‑budget roles after they were found to silently burn their token budget on hidden "thinking" output.
ResultExpert time‑to‑first‑token fell from 5–11s (initial reasoning model) to 0.15s p50.

Edge/cloud placement by latency and privacy

ProblemAlmost every stage could technically run in either place — where should the line actually go?
ChoiceVAD, STT, retrieval and TTS stay on the edge GPU; rewrite and generation run on cloud EU inference, where a larger model is worth the round‑trip.
ResultThe same placement rule was reused for every feature added after the PoV.

External dependencies behind a one‑function interface

ProblemLLM, STT and TTS providers change. A system wired directly to one of them is a system waiting to be rewritten.
ChoiceOne narrow function per capability — transcribe(), synthesize(), expert_completion() — with any provider swap confined to a single adapter file.
ResultSTT was swapped once and TTS four times — including a cloud excursion and a rollback — each time touching only its own adapter file.

Abstention as a shipped feature

ProblemA system that always produces an answer — even a wrong one — isn't trustworthy in a technical‑support context.
ChoiceA score‑gated coverage check plus an LLM‑as‑judge cascade (covered / partial / not covered); any escalation beyond the knowledge base needs explicit user consent.
ResultOff‑topic questions abstained 5/5 even with web search enabled; the judge was tested on three conditions of 35 items each — genuine answers, wrong context, and answers with a single altered fact — and got all 105 judgments right.
06

Problems solved

Retrieval quietly collapsed on follow‑ups

SymptomRecall on conversational follow‑ups fell to near zero (R@3 0.01–0.02) while single‑shot questions still worked fine.
Root causeThe small local model rewriting follow‑ups into standalone queries kept dropping the entity under discussion, and occasionally switched language.
FixMoved rewriting to a larger cloud model with the full conversation window — R@3 on that follow-up set recovered to 0.975. Hard‑coding the current topic into every query was tested as a shortcut and rejected: it broke abstention by making unrelated questions match too.

The transcript quietly rewrote technical terms

SymptomEnglish technical terms spoken inside Italian sentences came out as unrelated words, and retrieval then failed to match — no visible error, just an unjustified refusal to answer.
Root causeThe speech‑to‑text model was pinned to Italian, which "corrected" unfamiliar English terms instead of transcribing them.
FixSwapped in a code‑switching‑native ASR model behind the existing interface — the pipeline code didn't change, only the adapter.

A faster voice engine failed without an error

SymptomDuring testing, the microphone level moved but nothing was ever transcribed — an easy failure to miss, since nothing crashed.
Root causeA streaming TTS engine, measured at 0.101s time‑to‑first‑audio, shared the 12GB GPU with the ASR model; on the very first turn the ASR model ran out of memory, visible only in the service log.
FixRoot‑caused instead of patched around. Findings were fully documented and the approach frozen for future, higher‑VRAM hardware rather than shipped broken.

The web fallback returned thin answers

SymptomTurns that escalated to the web came back weak, on questions the open internet clearly covers.
Root causeNot the one assumed. The opening hypothesis was that too few results were being read; a twenty-minute measurement showed the count was fine and the depth was the problem — the engine returned only its own preview text, never the page behind it.
FixSwapped to a search API that returns extracted page content: 10/10 against 8/10 on the same questions, median context per turn up from ~1,300 to ~2,100 characters, and search latency down from ~2.6s to 1.4s. Deliberately with no automatic fallback between engines — in a lab, silent degradation to a different engine hides the fault instead of showing it.

Lesson: on shared cloud inference, latency is a moving target. A rewrite step once looked 10× slower than the day before; the cause was transient provider load, not a model limit. Re‑measure before concluding a component is the bottleneck.

07

What's next

Pronunciation lexicon (soon)

The acronym guard is built and deterministic, but each knowledge base starts with an empty lexicon — a new corpus cannot yet pronounce its own domain codes. Populating it is manual by design: the right rendering is decided by ear against a preview, not derivable from a rule. Nearest to done, and a prerequisite for closing the acronym work behind it.

Portability to Aruba Cloud (soon)

Move edge inference (STT/TTS) to Aruba GPU on Demand and the application runtime to Aruba Cloud, with embeddings and reranking served remotely. Worth stating plainly: that last part is not a lift-and-shift but a change to the placement rule itself, and it lands on the most sensitive component. The local reranker was chosen because its normalised scores make the abstention threshold trustworthy, and a remote reranker with flat, uniformly high scores was rejected earlier for exactly that reason. So the migration has to be measured against abstention, not just latency. First step is a minimal Dockerfile, to validate portability independently of the infrastructure move.

Validating retrieval anchors

An indexing bug meant LLM-generated Q&A "anchors" were paid for at every ingest but never reached the index — and retrieval held up fine without them. Before re-enabling them, an A/B test on a separate collection will check whether they earn back their cost, measured on false-abstention rate rather than an internal score. Cheap to run, and it either removes a recurring ingest cost or justifies it.

Streaming voice (blocked on hardware)

The current voice engine is synthesised in-process, sentence by sentence, and the chunks are concatenated. Serving the same voice model through a streaming inference server instead unlocks the streaming path the model natively has and the adapter does not use — and the gain is not only speed. Time-to-first-audio drops from ~2.2s to 0.101s, and intonation becomes continuous across sentences rather than restarting at every chunk, which is the audible difference. It is implemented, measured and documented, but does not fit on today's 12GB edge GPU: with the synthesis server running, the speech-to-text model hits CUDA out-of-memory on the first turn. Frozen for higher-VRAM hardware, with one prerequisite already identified — the synthesize() contract has to become async first, because the current thread bridge adds noise exactly on top of the metric that justifies the change.
